# Desktop 媒体加载优化（实验）

入口：设置 → Regram 设置 → 媒体。默认关闭，可随时切换。实现使用 Telegram Desktop 的 Qt、自动下载和流播放器；参考 [Regram iOS 同类实验](https://github.com/RegramDev/Regram-ios/blob/a5c80b6d5ff8b995cd6e4d5737a058dd894e3293/docs/media-loading-experiment.md)，不直接使用 Swift 或 HLS 调度器。

## 当前源码行为

- 普通历史及回复列表更新可见范围时合并调度。同方向继续滚动也刷新候选；每方向最多六个媒体项目，最多扫描 64 条消息，整个会话最多保留十二个当前预取资源。
- 照片沿用原生自动下载权限；文档预取缩略图，不能流播放的文件沿用原生自动下载；可流播放的视频使用已有 VideoPreload 前缀缓存，并检查自动播放权限。
- 资源按实际媒体对象去重。离开窗口后保留 1.5 秒，最多三个待释放项目。视频前缀任务由该窗口持有，释放时取消自己的请求；共享照片和文档加载器由原生引擎管理，不因预取退出而取消用户的手动下载。
- 修改自动下载设置后清除预取任务并按新权限重建。后台和关闭实验时释放预取；会话销毁时清理调度器。
- 每会话最多两个自动播放项目，可见中央区域优先。离开可见区域、窗口不可见、后台或原生省电策略暂停动画时撤销准入。手动播放及画廊持有播放器锁时保留原生行为。
- 暂停时降低流实例优先级；持续暂停 1.5 秒后释放聊天实例。已共享的播放器在会话内最多保留一个、最长 1.5 秒，返回时复用；后台和实验开关变化时清空保留池。
- MTP 下载队列按数据中心最多同时启动两个自动任务，存在在途流播放请求时限制为一个。已经在途的请求完成后再恢复额度；新手动下载可获得首次请求机会，后续仍遵循原生队列优先级。
- 可见候选容量、延迟保留容量和播放容量分别限制。预取不会在主线程额外运行关键词或正则过滤；使用列表已建立的显示状态。

## 默认视频画质

同页可选择自动、最高可用、最低可用。独立于实验开关。开始播放时通过原生 quality 列表选择；单视频手动选择及完整本地文件优先，保留原生 inline 解码面积限制。

切换默认值影响后续开始的播放；已经播放的视频及用户手动选择继续沿用原生状态。不能将更低画质带来的加载时间变化当作同画质加速。

## 验证状态与边界

2026-10-12：新增源码已进入 arm64 Release 前置编译。尚无本轮新增调度器的真实滚动、帧率、首帧、网络和内存测量结果；旧安装包不包含本轮代码。

Qt 的共享读取、画廊锁和有限保留池提供桌面对应行为。当前没有新增 iOS 式 HLS playlist owner、独立解码帧信号或系统内存警告回调；平台现有缓存、播放器锁及省电机制继续负责相应行为。不能声明两种引擎完全等价。

运行回归需要同账号副本、同网络、同自动下载策略及同画质，对照开关。分别记录冷缓存和热缓存，检查长历史同方向滚动、快速回滑、三个以上视频、手动下载并存、设置变化、后台恢复、画廊往返及注销账号。安装包构建完成后记录实际结果。
