# Regram Desktop 全功能移植实施计划

计划日期：2026-10-03。目标：把当前 Regram iOS 中所有适用于桌面的已加入功能带到 **Regram Desktop**；平台没有对应能力的项目明确排除，可等价实现的项目按桌面方式适配。

配套文档：[逐项功能矩阵](regram-desktop-feature-matrix.md)包含 **129 项实施／验收条目、14 项排除或替代说明**；来源为[iOS 功能清单](features.md)。条目是工作追踪单位，不等于 129 个互不重叠的独立产品功能。

2026-10-04 起在本仓库按 M0～M8 持续实施。已建立独立移植分支初始固定 v7.2.9 基线，现已同步 v7.3.0，构建依赖准备完成。范围追加为 Nagram-Qt 与 AyuGramDesktop 全部功能；macOS 保留原版 Qt 界面；源码整合与 Debug 编译仍在进行，尚未完成登录或逐项验收。实际进度与各平台结果见[实施与验收记录](progress.md)，参考项目的固定版本与接入点见[源码参考](references.md)。矩阵中的“继承并补齐”仍须逐项验收。

**2. 已经可以复用的部分**

Desktop v7.2.9 已有富文本编辑器、文章媒体、表格、公式、HTML 导入导出及任务交互基础。此部分采用“测试样本比对 → 记录缺口 → 补齐差异”的路线，详见[上游更新记录](https://github.com/telegramdesktop/tdesktop/blob/v7.2.9/changelog.txt)及[任务交互实现](https://github.com/telegramdesktop/tdesktop/blob/v7.2.9/Telegram/SourceFiles/api/api_rich_tasks.cpp)。

翻译也已有 [TranslateProvider](https://github.com/telegramdesktop/tdesktop/blob/v7.2.9/Telegram/SourceFiles/lang/translate_provider.cpp)和 [URL provider](https://github.com/telegramdesktop/tdesktop/blob/v7.2.9/Telegram/SourceFiles/lang/translate_url_provider.cpp)，因此优先扩展上游接口，补齐服务选择、发送前翻译及队列管理。不能据此认为所有 iOS 翻译行为已经满足。

可从 iOS 复用：功能规则、默认值的含义、菜单顺序规范、语言文案、注册时间估算数据、过滤规则导出格式的转换逻辑、性能策略测试场景。需要重写：Swift／UIKit 界面、Postbox 接入、播放器、系统通知与设备接口。两端可以共享协议规范与测试样本，不共享账户登录文件。

**3. 桌面产品结构与默认行为**

设置中心分为消息过滤、隐私与本地保留、菜单与输入、翻译与转写、界面与分组、资料与快拍、媒体与网络、通知、应用管理、实验功能。已有上游设置优先复用或链接到原页面，避免同一个值出现两套互不一致的控制。

| 范围 | 保存与作用方式 |
| --- | --- |
| 应用级 | 外观、窗口／导航布局、图标与浏览器偏好 |
| 账户级 | 过滤规则、隐藏用户、隐私、通知、翻译偏好和本地保留策略；账户间可显式复制规则 |
| 会话级 | 过滤例外、防撤回、发送前翻译目标语言；支持主题定位，不把不同会话混为一谈 |
| 设备级 | 摄像头、麦克风、平台服务及硬件相关选项 |
| 单视频／临时会话 | 手动画质、播放状态、请求归属；不能被迟到的全局默认或旧回调覆盖 |

新增会改变发送、上报、保存行为的开关默认关闭，包括幽灵模式、防撤回、本地 Premium、自动格式、盘古空格和默认禁用链接预览。实验加载优化默认关闭；视频画质默认自动，最近贴纸默认 20。其余默认值沿用上游；需要与 iOS 不同的地方在设置规格中说明。

桌面交互保留原有键盘和鼠标习惯：右键代替长按，按钮／右键代替左滑管理，侧栏折叠代替隐藏手机底栏。底部分组作为一个可选桌面布局实现。双击编辑是可选动作，不覆盖默认文字选择；输入法候选确认不得触发发送。

**4. 代码与存储架构**

以下是待创建的建议目录；具体构建声明沿用上游风格。Regram 新逻辑集中在自己的模块，只有必要调用点进入上游文件，并标注 `MARK: Regram`。

```text
Telegram/SourceFiles/regram/
  settings/       设置定义、迁移、搜索入口和功能可用性
  filters/        规则、消息判定、缓存与导入导出
  privacy/        本地隐私策略和账户作用域
  archive/        本地保留内容、索引、读取、清除和容量管理
  messages/       菜单动作、发送变换和消息详情
  translation/    翻译／转写接口扩展、队列和缓存
  appearance/     导航、列表、资料和外观设置
  media/          画质、传输偏好及实验调度策略
  notifications/  通知分类、内容选择和任务生命周期
  platform/       系统通知、设备、浏览器与图标适配
  diagnostics/    可关闭的性能指标与诊断
```

模块设计采用以下约束：

- 过滤只改变本机显示与用户选择的通知行为，不删除云端消息、不伪造服务器已读数；需要访问原始消息的上游功能仍保留原数据。
- 过滤、通知和本地保留展示使用同一份消息文本／发送者判定，富文本有统一的可检索文本提取方式。
- 所有异步任务都有账户和生命周期归属；取消、切账户、编辑消息或销毁窗口后，旧结果不能提交到新对象。
- 本地保留记录与正常云端消息分开表示；本地 Premium 展示与真实服务器权限分开判断。
- 设置、规则与保留库有各自的版本号和迁移；写入中断可恢复，不通过删除已有数据来绕过升级问题。
- 含消息内容的保留库接入经过验证的账户本地加密存储能力；M0 验证具体 API，避免自行设计加密格式。普通缓存清理和保留库删除是不同操作。
- C++ 策略模块尽量独立于 Qt 界面，便于用虚构消息、可控时钟验证规则与竞态。

主要上游接入面已经在固定基线中找到，列为开工导航而非最终补丁清单：

| 功能 | 上游起点 |
| --- | --- |

| 消息显示与上下文菜单 | `history/view/history_view_list_widget.cpp`、`history_view_context_menu.cpp` |
| 消息生命周期 | `data/data_session.cpp`、`data/data_histories.cpp`、`api/api_updates.cpp` |
| 输入活动与快拍 | `api/api_send_progress.cpp`、`data/data_stories.cpp` |

**5. iOS 配置与规则兼容**

第一版迁移支持现有过滤规则 JSON，以及明确提供的 Regram 偏好文件；不直接读 iOS App Group、Keychain、Postbox 或 Telegram 登录资料。iOS 尚未导出的设置，在 Desktop 中配置，不能声称已经自动迁移。

| 问题 | 计划处理 |
| --- | --- |
| iOS 旧规则结构 | 读取现有 `id / pattern / isRegex / peerIds`，经转换后进入统一版本化格式；iOS 当前实现不随本计划改动 |
| 账户和会话标识 | 对外格式用会话类型及服务器 ID 的十进制字符串；内部 ID 必须经适配器转换，禁止直接把两端打包后的整数等同 |
| 64 位数字精度 | 旧导入要保留精确整数；新格式不依赖 JSON 浮点表示保存 ID |
| 无法识别的范围 | 显示待处理项并保持不生效，不能默默退化成“所有对话” |
| 正则引擎差异 | M0 用 ICU 兼容测试集评估实现；非兼容表达式要指出原因，不能导入成功但匹配含义改变 |
| 合并和去重 | 内容、类型、规范化作用域相同才视为完全重复；不同范围的冲突在导入预览中列明 |
| 文本与实体 | 转义、换行、UTF-16 偏移、组合表情及 RTL 文本都列入样本 |
| 导出边界 | 导出规则和可移植偏好；不包含认证材料、消息正文、系统设备 ID 或转写服务密钥 |

保留对旧 iOS 导出文件的兼容不等于双向无损同步：Desktop 新配置格式若要由 iOS 导入，需要另行添加兼容导出或更新 iOS 导入器。本项目先保证已有规则能可靠迁入，云端自动同步不在本次范围。

**6. 开发阶段与完成门槛**

M0～M8 是交付顺序，不是承诺工期。M0 完成后按实际构建成本和验证出的缺口估算工作量。每阶段可交付内部版本；只有全部适用条目验收后才称为全功能移植完成。

| 阶段 | 内容和主要条目 | 依赖 | 阶段完成门槛 |
| --- | --- | --- | --- |
| M0 基础工程与可行性验证 | 固定版本、原版编译、独立应用身份／数据目录、设置骨架、平台能力表；规则导入和保留库原型；RD-A01 起步 | 无 | 至少一平台可运行，各目标平台有构建路径；原版行为基线和高风险原型有记录 |
| M1 过滤与隐藏用户 | RD-F01～F12；设置、资料页、消息菜单的最小接入 | M0 | 收到消息→匹配→列表／聊天刷新→改规则恢复完整闭环；导入兼容和账户隔离通过 |
| M2 菜单、输入与富文本 | RD-C01～C09、RD-I01～I07、RD-R01～R04／R06～R09 | M0；菜单快捷过滤依赖 M1 | 发送、编辑、撤销、草稿、输入法、富文本跨端样本验证完成 |
| M3 界面、资料、快拍与应用外观 | RD-U、RD-D、RD-I08～I09、RD-P07、RD-A01～A03／A05～A10 | M0；过滤预览依赖 M1 | 所有相关入口可发现；窗口缩放、主题、键盘和平台差异验收完成 |
| M4 翻译与转写 | RD-T01～T09、RD-R11 的翻译部分 | M0、M2 的输入内容规范 | 单条／整聊／置顶／发送前翻译和两类转写有可运行后端；失败、取消、换语言正确 |
| M5 隐私、本地保留与通知 | RD-P01～P06／P08～P11、RD-N01～N08、RD-A04／A12、RD-R11 的保留部分 | M0 保留原型、M1、M4 的统一内容判定 | 重启可查看保留内容；主动删除、清除、账户切换、真实通知与控制同步全部验证 |
| M6 媒体、设备与网络 | RD-M01～M12、RD-A11、RD-R05／R10 | M0；M2 富文本规范；保留与缓存联动依赖 M5 | 图片／贴纸／画质／设备／传输配置在目标平台有效，富文本媒体路径正常 |
| M7 加载性能专项 | RD-L01～L11；复用 M1、M4、M6 的缓存与队列 | M1、M4、M6 | 冷热缓存分开对照，性能数据可复核，无饥饿、泄漏、跨窗口错配；开关能完整回退 |
| M8 全量验收与发布 | 矩阵逐项关闭缺口，三平台构建、安装升级、签名与更新、源码交付 | M1～M7 | 每项有平台结果和证据；没有被“上游已有”掩盖的缺口；发行包确由验证的源码生成 |

可并行的工作：M0 后，M1、M2、M3 的基础部分可以按独立模块并行；M4 可以在内容接口确定后推进。保留库设计不能等到 M5 才开始，M0 必须先验证。M7 需要稳定功能和测量基线，不与大量 UI 改动混在同一批测试里。

**7. 需要提前验证的设计点**

| 设计点 | 需要产出的结果 | 最迟决定时间 |
| --- | --- | --- |
| 持久防撤回 | 虚构内容的写入、删除状态、重启读取、主动清除原型；定位账户加密存储接口 | M0 结束 |
| 过滤一致性 | 列出聊天、主题、评论、搜索、预览、通知、保留库分别如何消费过滤结果；注明与未读数的关系 | M1 开始前 |
| 正则兼容 | iOS 规则样本的通过／不支持清单、超长文本与复杂表达式预算、所选引擎依赖 | M0 结束 |
| 富文本差异 | 对矩阵 RD-R 的每项标注上游已满足、需要补齐、依赖服务端的具体情况 | M0 初查，M2 关闭编辑缺口 |
| 独立转写 | 选定可持续使用的服务／本地引擎，说明三平台覆盖、资源成本和分发依赖 | M4 实现前 |
| 平台特有能力 | 系统翻译、图标切换、WebView、摄像头、通知、Force TCP 的实际能力表 | M0 初查，对应阶段实测 |
| 保留库容量 | 可配置期限／容量、超限行为及用户清除入口；与普通下载缓存分开 | M5 实现前 |
| 性能预算 | 固定机器和样本，确定时间、内存、流量及后台 CPU 的允许回归阈值 | M7 实验前 |

能力未确认时保留该条目并安排验证；确认不可实现后只排除具体子项，并在矩阵写出证据、受影响平台及替代方案。这样可以履行“所有能移植的都做”，而不把未知当作支持或不支持。

**8. 验收与测试计划**

| 范围 | 必测场景 |
| --- | --- |
| 规则与导入 | 普通／正则、Unicode／简繁／RTL、无效与复杂表达式、范围、去重、64 位 ID、损坏文件、旧版本转换 |
| 多账户与窗口 | 同一会话多窗口、不同账户相似会话、切换／退出账户、后台任务完成、设置实时同步 |
| 消息操作 | 文本、媒体组、富文本、转发、回复、主题、计划消息、无权限操作、不可复读的特殊消息 |
| 输入 | 拼音／日文输入法、快捷键、选区、组合表情、格式实体、重复发送变换、撤销、草稿恢复 |
| 本地保留 | 别人撤回、自己删除、TTL 到期、未收到原消息、重启、版本升级、磁盘满、缓存清理、退出及清除全部数据 |
| 翻译与转写 | 网络失败、限额、取消、长内容、语言变化、消息编辑、过期结果、音频损坏、模型／系统能力缺失 |
| 通知 | 前台／后台／最小化／系统锁定、隐私预览、纯附件、提及、置顶、重复消息、已读／删除同步、通知权限关闭 |
| 媒体与设备 | 冷／热缓存、多视频、手动下载与播放并存、变更画质、查看器切换、摄像头和麦克风拔插 |
| 桌面 UI | 窄／宽窗口、高 DPI、多显示器、深浅主题、键盘导航、减少动画、各系统菜单与托盘行为 |
| 富文本跨端 | 用同一批测试消息在 iOS 和 Desktop 间发送／编辑／复制，覆盖表格合并、任务、媒体、公式、草稿和翻译 |
| 安装与数据隔离 | 官方 Telegram 与 Regram 同时运行；安装、覆盖升级、卸载／重装、数据清除均不影响另一客户端 |

规则、转换、队列和存储迁移使用有意义的单元／集成测试；UI 与系统能力通过实际应用验证。新增简单文案或可逆视觉调整不单独堆叠模拟实现的测试。

性能试验必须比较同设备、同账户、同网络、同画质、同自动下载策略的开关状态，冷热缓存分开。记录消息可见时间、可显示的真实首帧、滚动卡顿、峰值内存、CPU、流量、取消延迟和手动任务等待时间。每个主要场景做足够重复以给出中位数与尾延迟，M7 前固定采样方案；没有测得收益就不写“提速”。

每个完成项的验收记录包含：功能 ID、源码提交、系统／架构、构建模式、测试步骤、预期／实际结果、证据路径及未覆盖场景。状态使用“待开始／开发中／待验收／通过／受限／排除”，不能用一个总勾选掩盖某个平台尚未测试。

**9. 构建、品牌与发行**

构建流程引用固定基线的官方文档：[macOS](https://github.com/telegramdesktop/tdesktop/blob/v7.2.9/docs/building-mac.md)、[Windows](https://github.com/telegramdesktop/tdesktop/blob/v7.2.9/docs/building-win.md)、[Linux](https://github.com/telegramdesktop/tdesktop/blob/v7.2.9/docs/building-linux.md)。具体 SDK、编译器、Qt 和子模块版本在 M0 锁定并记录，后续以实际成功构建的组合为准。

M0 的应用身份清单包括：应用名、bundle／应用 ID、进程互斥标识、用户数据目录、便携目录、系统通知标识、托盘、URL scheme、文件关联、卸载与更新目标。默认与官方客户端共存，不自动占用用户现有默认链接处理方式。

开发阶段使用独立 Regram 数据目录，禁用会把程序替换回官方包的上游自动更新路径。M8 建立 Regram 自有更新元数据与签名验证、渠道及升级恢复测试；更新基础设施未就绪时交付明确标记的手动更新包，不能指向官方更新服务。

API 配置、签名材料与测试账户数据存入忽略的本地目录或构建环境配置；公共仓库只保留模板。品牌资源和已有第三方归属信息随源码维护。Windows、macOS、Linux 安装包分别记录 SHA-256、构建来源和验证结果；只有实际完成的系统包才列为已交付。

**11. 计划维护与下一工作区的交接**

- 功能任务以矩阵 ID 建立；跨模块任务可以对应多个 ID，但每个适用 ID 都必须有完成记录。
- 新增上游修改保持小范围，同一阶段内按功能形成可审查提交；每次同步上游先构建再做重点回归。
- 每阶段更新实际完成数、平台验证状态和剩余差异。移除某个条目必须附实际不可用证据，不能只写“成本高”。
- 将本计划和矩阵带入 Desktop 仓库时，保留 iOS 源码基准，并把来源相对链接改为固定版本的 iOS 源码链接或归档文档。
- 开工从 START-01 开始；本仓库已开始 M0，按实施记录推进至 M8，未验收项目保持开放。

原计划证据范围：本地 iOS 功能与源码核对；官方 Desktop 正式版本、目录及关键源码接口核对。新增实现、构建、运行及性能证据统一记录在实施与验收记录中。所列阶段不代表已经测通。
